01

ASIC 起点与复现验证

TARS-mini 是 TARS NPU 的第一个端到端切片：单核，接收 512 位描述符（V1.3.1 格式）。它在本项目开始前已完成到契约 v0.4，本项目没有改动它的 ASIC 行为。

部分内容
契约v0.4。contract.py 和 golden.py 是它的可执行形式，golden 模型里没有任何微架构参数（R、C、NB、OT…），只规定结果比特。
RTLR×C INT8 输出驻留脉动阵列、epilogue、行引擎（vpu_lane + fold）、扩展单元 tm_xpu（ELT/ROPE/FDOT/QUANT/GEMV）、fp32 流水单元
验证体系748 个测试；随机队列 fuzz（5 种阵列形状、随机反压和延迟、覆盖断言）；141 个变异体；fp 单元约 60 万向量
时序ASAP7 + Yosys/ABC + 自写 sta.py，每级 ≤650 ps（1 GHz），最差 644 ps
Qwen24 层 + head，一个 decode 步 2,730 个描述符；理想端口 57.3 M 周期，LPDDR4X（DRAMsim3）下 76.5 M 周期，1 GHz 时约 76 ms/token

本项目中的复现

  • 工具链：在没有 sudo 的 AlmaLinux 8 上装好 Verilator 5.052、Yosys 0.69、sv2v、ASAP7 库和 DRAMsim3。解决了 torch 加载旧 libstdc++、CMake 4 拒绝 DRAMsim3、sv2v 需要 glibc 2.34 三个问题。
  • 复现结果：333 个非 RTL 测试和 RTL fp 测试通过；golden 全模型生成的 token [14184,156431,220662,75312] 与原记录一致；时序校准为 170 ps 加法器、580 ps 乘法器，文档记录是 167/578 ps。
  • 真实权重：载入 Qwen3.5-0.8B。golden 输出 " Paris."。与 fp32 transformers 相比，argmax 17/17 一致，logits 余弦相似度最小 0.9932、平均 0.9972；逐层相对误差中位数 1.8e-7。
  • 没有完成：ASIC 构建的全模型 RTL decode 仿真跑到 1000 万周期时，按要求停掉（跑完要 6–8 小时）。此后 Verilator 默认多线程运行（TM_THREADS）。

FPGA 移植：把 604k LUT 压进 117k

v1.1读突发

改动：读请求先进输入寄存器（消除 mr_addr→mr_ready 组合环），连续地址攒成最多 16 拍的突发，不跨 4 KB。写队列带年龄掩码，只有真正和未完成写地址重叠的读才等待。新增 7 个性能计数器。

效果：AXI 读事务从 57 M 降到 18 M，平均每个突发 3.1 拍。仿真只快 18%，板上快了 2.9 倍：仿真模型低估了真实 DDR 处理零碎请求的代价。

分块 prefill：结果逐比特正确，但板上更慢（1.6–1.8 s/token）。M≥2 走 8×2 阵列，受算力限制，激活值要为每 2 列输出重读一遍。当时默认关闭。

v1.2v1.3先找准瓶颈

v1.2 放弃：只做"更长突发 + 更多在途读"，仿真里几乎没有收益。

定位：建了贴近板子的仿真内存模型（+nout=16 +blat=50，1.55 周期/拍，板上实测 1.58）。发现约 1/3 时间花在 LA 状态更新：3 路交错读，每个突发只有 1 拍，被 HP 口在途突发数限制在 0.33 拍/周期。

桥：4 路交错流各自收集成突发，平均约 25 拍，BRAM 重排序缓冲按原顺序把数据还给核心；在途读从 64 增加到 128；ELT 的标量操作数不再每拍重读。

为什么不放大阵列：PE 改 DSP 后，16×8 阵列仍要 133k LUT（114%），因为 epilogue、行读出 mux 和 loader 表都随 R/C 增长。改做批量 GEMV：权重只读一次，每拍 16 个权重同时乘最多 8 个 token。8 个 token 一块时，每 token 比 decode 快 3.3 倍。分块大小相应改成 8/4。

上板：decode 只快 19%，仿真预期 29%。计数器显示写成了新瓶颈：每 token 有 16 M 周期在等写。

v1.4写突发

连续的写攒成最多 16 拍的突发，GEMV 逐元素的 4 B 写按字节使能合并成整拍，最多 16 个写突发在途；读写冒险按 16 B 精度检查。写等待从 16 M 降到 0.15 M 周期，decode 快 18%，与事先预测的 15–20% 吻合。

v2.032 B 读口

改动：桥改成 32 B 拍，两个 16 B 半拍共享一个重排序槽；pl_clk1 = 200 MHz 驱动 HP0，SmartConnect 做 256→128 位宽和时钟转换，设备树覆盖里加 clocking1；GEMV 增加 WIDE 模式，每拍 32 B。

问题 1：第一版反而更慢。突发上限 64 个 32 B 拍正好耗光 128 个在途读信用，把上限改为 16 拍解决。

问题 2：第一次实现时 LUT 到 94.2%，布局失败。瘦身措施：阵列 PE 改 DSP；阵列 loader 的在途读降到 32（GEMV 和行引擎保持 128）；请求队列 NQ=256；GEMV 窄模式放置 mux 从 8 路合成 1 路；再加 AreaOptimized_high 综合策略。最终 LUT 89.4%，WNS +0.086 ns，DSP 668，BRAM 40.5。

效果：decode 快 40%，36.4 M 周期/token。

测量DDR 带宽实测

v2.0 只用了 KV260 DDR4 理论带宽（19.2 GB/s）的约 1/6。在继续加宽读口之前，先单独做了一个比特流 fpga/kv260_ddrbw：四个 AXI 流量发生器分别直连 HP0–HP3，在 200 / 250 / 333 MHz 下测读写带宽。

结论数据
每个 HP 口的上限 = 16 B × 时钟3.2 GB/s @200，4.0 @250，5.2 @333
每口约 70 M 事务/秒，短突发吃亏16 B 单拍突发只有 1.15 GB/s，要长突发才能跑满
HP1 和 HP2 共用一个 DDRC 端口两者合计最多 8.3 GB/s
四口并用最好12.3–12.8 GB/s（200–250 MHz）；333 MHz 反而降到 10.7
空载读延迟约 140–155 ns

所以带宽的路线是：多口并行 + 250 MHz + 长突发，而不是提高单口时钟。

v3.0双口 64 B

改动：核心读口加宽到 64 B/拍；桥按物理地址第 10 位把突发分给两个读主口，HP0 和 HP3 各 128 位 @ 250 MHz，通过核心顶层内的 tm_hpr（异步 FIFO）跨时钟，不经过 SmartConnect；写口 256 位经 SmartConnect 到 HP1。GEMV 一次处理 4 行、每拍 64 B 权重，prefill 分块随之改为 4 个 token。

问题：AR FIFO 用 LUTRAM 时出现跨时钟路径，改成 BRAM；DDR 测试比特流里设备树把 HPM0 设成了 128 位而设计是 32 位，寄存器读到错的字节，改 afi 配置解决。

效果：decode 0.36 → 0.21 s/token，读延迟 66 周期；LUT 升到 90.8%，已经贴墙。

分析LUT 从哪里来：FP16 还是去掉阵列

v3.0 的仿真剖析：GEMV 占 53% 时间，接近每周期 1 拍；ELT 25%、FDOT 17.5%，只有 0.2–0.3 拍/周期。要再快，读口必须再加宽，但 LUT 只剩 9%。

FP16 lane 可行吗：在 transformers 里把 Gated DeltaNet 递推换成逐 token 循环，测 2,048 token 英文和 1,642 token 中文。只把状态存成 FP16 时，top-1 一致率 97–100%，KL 约 1e-3；全 FP16 运算也接近。BF16 状态明显差一档（top-1 94%，NLL +0.05）。这些偏差都远小于现有 W8A8 量化本身（top-1 83–92%）。但 fp32 单元已经共享过，换成 FP16 省不了多少 LUT，而且会破坏现有契约的逐比特一致。

选择：Qwen 不用 conv，GEMM 都能用 GEMV 分批完成，所以去掉脉动阵列（核心参数 ARR=0）。conv 和 K > 4096 的 GEMM 返回 E_OPCODE，golden 模型加了对应的 gemv_only 配置，契约其余部分不变。综合 LUT 从 101k 降到 89k，腾出的空间用来加宽读口。

v3.2四口 128 B，无阵列

改动：核心读口 128 B/拍；桥按物理地址 [11:10] 把 1 KB 突发分到四个读主口：HP0、HP3、HP2 直连，第四口和写口经 SmartConnect 到 HP1；重排序缓冲拆成高低两个 512 位 bank，两个通道各取一半；GEMV 每拍 128 B、一次 4 行；编译器分配对齐从 64 B 改为 128 B。

问题 1：ARR=0 后 softmax M=2 只算了 1 行。GEMV 的分批行数上限误用到了行操作上，限定只对 GEMV 生效。

问题 2：完整回归 32 个失败，全是 ELT/ROPE/行操作挂死。读突发上限从 16 拍改成 8 拍时，写突发计数器共用了同一个位宽参数，16 拍的写回绕成 0，发出 awlen=255。写计数器改用自己的位宽。

问题 3：板上自检的随机程序仍按"有阵列"生成，conv 被硬件正确拒绝，却被判失败。导出脚本改按 gemv_only 生成。

问题 4：重启后 hugepage 分配失败。Linux 把一个 hugepage 放在了物理地址 0，而驱动把 PFN 0 当成"非 root 读不到页号"。ZynqMP 的 DDR 从 0 开始，PFN 0 是合法的，修正检查并在板上重编 libtmdrv.so。另外板子连续运行两天后内存碎片化，凑不齐 528 个 hugepage，需要重启。

效果：回归 386 通过 / 22 跳过（conv 与阵列专用用例），核心 testbench 425/425；时序 WNS +0.176 ns，LUT 86.0%，DSP 879，BRAM 118。板上 ALL PASS，decode 15.7 M 周期 = 0.16 s/token，示例对话 4.5 s。prefill 几乎没变（0.115 s），因为分块 GEMV 已受算力而非带宽限制。

v3.2bFDOT 各遍重叠

瓶颈：v3.2 之后 GEMV 已贴近读口带宽，注意力里的 FDOT（QKT 和 PV）变成长上下文时的主要开销。每一遍结束时要等折叠（fold）和读出完成，下一遍才能开始。

改动：一遍结束后不再挡住下一遍，折叠和读出在后台进行；NT 方向把 A 的一行（K ≤ 1024）在第一次输出后留在 BRAM 里，读量减半；NN 方向每 4 个 k 才读一次 A。每个 lane 的累加顺序不变，结果逐比特不变。只改 FPGA 构建（TM_FPGA），VERSION 寄存器仍是 0x00030100。

测试漏洞：去掉折叠的保护条件时，原有测试全部通过。原因是输出队列从来没被写满。加了 +wstall=100 的 testbench 模式把输出队列塞满，才抓到这个问题。

效果：Qwen3-0.6B 在位置 16 快 1.10×、位置 250 快 1.40×；Qwen3.5-0.8B 快 1.05–1.10×。WNS +0.187 ns，LUT 85.65%，BRAM 120。

v3.3FDOT 每周期 16 次乘加

改动：4 组 lane 轮流累加，每个 lane 保持 3 周期加法和契约规定的 k 顺序。NT 一次处理 4 个 key、128 B 读，A 的一行放在 GEMV 空闲的 x 缓冲里，一组的数据按地址从 FIFO 取；NN 一次处理 64 列。其他形状仍走原来的 4 lane 路径。

问题：第一版 LUT 99%，布局失败。把 lane 改成带有效位的小 LUT 存储器后才放得下。

效果：相对上一版，Qwen3-0.6B 在位置 16 快 1.23×、位置 250 快 2.28×；Qwen3.5-0.8B 快 1.21–1.36×，decode 13.2–13.6 M 周期 = 0.13 s/token。WNS +0.013 ns，LUT 89.55%，DSP 903，BRAM 118，VERSION 0x00030300。这是当前的默认固件。

测量分算子周期计数器

为了知道下一步该优化什么，在 v3.3 上加了一组计数器（PROFILE_CAP = 0x50524601）：按 GEMV、ELT、FDOT NT/NN、RoPE、QUANT、Norm、Softmax、ACT 和取指/校验开销分别累计周期，各类之和必须正好等于核心周期。run.sh profile 读取它们；旧固件只给总读写量和等待计数。

正确性：加计数器前后所有共同采样位置的 logits 哈希相同，首次 decode 测量慢 0.005–0.103%；一次 Qwen3 位置 250 的重复测量慢约 0.60%，不能据此断言计数器零开销。两次独立实现的 LUT 相差 88 个（89.62%），并非孤立的计数器面积估计；WNS +0.044 ns。

结论：Qwen3-0.6B 短上下文时 GEMV 占 76%，到位置 250 时 FDOT 升到 32%；Qwen3.5-0.8B 的 ELT（DeltaNet 状态更新）占 35–36%，读带宽只有约 6.9 GB/s。详见 docs/profiling_v33/。

v3.4FP16 DeltaNet 状态（实验）

动机：剖析显示 Qwen3.5 的 ELT 主要在读写 DeltaNet 状态 S。把 S 存成 FP16，读写量能少一半吗？

改动：只有 S 以 packed IEEE FP16 存储，衰减和更新写回时按最近偶数舍入；读回后乘、加、归一化和 SFU 都仍是 FP32。描述符用以前保留的编码选 FP16 的 ELT 输入/输出和 FDOT NN 的 B。导出时用 --state-dtype fp16，需要 VERSION 0x00030400，运行时会拒绝旧固件。

验证：板上 FP32 和 FP16 两份导出各自与 golden 逐比特一致；另用"FP32 程序 + NumPy 只对 S 舍入"的影子模型核对，结果逐比特相同。WNS +0.008 ns，LUT 90.50%。

结果：反而慢了 3%（decode 131.6 → 135.7 ms），prefill 慢 2.2%。ELT 仍是每次 16 B 读取 4 个半精度值，请求数没变，转换还增加了延迟；读量每步只少约 3.9 MB，写量少 18 MB。精度上约 10% 的位置 top-1 改变（英文 90.87%、中文 89.08% 一致）。所以默认仍用 FP32，v3.4 没有替换默认固件，只在板上 firmware_v34/ 存档。详见 docs/fp16_state_v34/。

每一版固定的验证流程

  1. 修改 RTL，lint。
  2. 两套 RTL 回归各 416 项：核心 testbench，以及经 KV260 顶层、页面打乱、AXI 随机延迟。
  3. 用板级内存模型跑 2 层真实维度模型：逐比特一致，并测周期数。
  4. Vivado 实现，打包 bit.bin 和 dtbo。
  5. 上板依次跑硬件测试、逐 token 自检、分块自检，全部 ALL PASS 后才替换默认固件。旧固件保留在 firmware_v1/_v11/_v14/_v20/_v30。

换一个模型：Qwen3-0.6B

更多模型与功能：MTP 投机解码、Gemma 3 1B、按模型启动

Qwen3.5-0.8B 的 MTP 投机解码（2026-11-06）

Qwen3.5-0.8B 的 checkpoint 带一个多 token 预测头（一层门控注意力，2,000 万参数），在 NPU 上作为草稿模型运行。每一轮用一个两行的块同时验证 [当前 token, 草稿]：猜中得到两个 token，猜错得到一个。DeltaNet 状态不做快照：验证的第二个 token 写到第二份状态，猜中时两份状态互换，所以猜错不需要拷贝。贪心输出与普通解码逐比特相同，板上自检和多轮对话都核对过，RTL 不用改。

默认关闭：一轮的代价约等于 1.76 个普通步（注意力和递推随验证行数增加，草稿还要再读一遍 254 MB 的输出层），要约 77% 的命中率才不亏。v3.3 上 9 类提示词平均 0.97×，最好的 JSON 列表 1.13×。

给未来迭代的启示

方法

  1. 契约和 golden 是大胆优化的底气。golden 里没有微架构参数，所以共享 SFU、关闭行重叠、改桥、改读口宽度都只改变周期，可以放心做，最后用逐比特对比兜底。
  2. 验证要证明自己测到了改动。每加一条新路径就植入一个 bug，看测试能否抓到。SFU、三个端口和 loader 测试的问题都是这样发现的。
  3. 先测量瓶颈，再选方案。v1.2 盲目加长突发没有收益；有了计数器和校准过的模型，v1.4 预测快 15–20%，实测 18%。性能计数器应该从第一版比特流就带上。
  4. 仿真内存模型必须对齐真机。理想端口预测 0.85 s/token，真机是 2.6 s。换新平台时，第一件事是实测延迟和带宽，再用它校准模型。

FPGA 架构

  1. ASIC 的"每个 lane 一套完整 fp 流水线"在 FPGA 上不可行。到 100 MHz 要反过来用时间换面积：共享 SFU，用 LUTRAM 和 BRAM 存储，跨单元借用空闲的加法器和 recip。
  2. 存储结构决定面积。hbuf 一项就占 125k LUT。从一开始就按单写口 LUTRAM 或 BRAM 加寄存读来写存储。
  3. LUT 是墙，DSP 相对宽裕（v3.2 用 879/1248）。要提算力，优先选"权重只读一次、乘法放 DSP"的形状，而不是放大阵列。为目标模型删掉用不到的通用单元（v3.2 去掉阵列省了约 12k LUT）比精打细算更有效；代价是通用性，要在契约和 golden 里显式写成一种配置。
  4. decode 受带宽限制，而带宽要按平台实测来规划。先用独立比特流测出"每口 16 B × 时钟、四口最好、HP1/HP2 共享"，v3.0 和 v3.2 的设计都直接来自这张表。后续方向：INT4 权重（需要新契约）、把 LA 递推状态放到片上、ELT/FDOT 也用宽读口。

工程和板上操作

  1. 机器资源要算账。31 GB 内存上同时跑 Vivado、多个 Verilator 构建和长仿真会被 OOM 打断。控制编译并发，大任务错开运行。
  2. 不用会匹配到自己的 pgrep -f/pkill -f。改用 ps aux | grep "[p]attern"，或者按 PID 操作。
  3. 构建或回归运行期间不改 RTL，否则各个构建会读到不同版本的源码。
  4. 上板前确认没有人在用 PL。重载比特流会清空页表，正在跑的进程会访问错误的物理地址。
  5. Linux 侧的顺序依赖要写成脚本检查。先加载比特流再分配 hugepage；访问 PL 前确认 fpga0 处于 operating 状态。仿真覆盖不到这类问题。
  6. 改一个参数时，查清所有共用它的地方。v3.2 的读突发上限和写计数器共用一个位宽参数，只改读侧就让写侧溢出。不同用途的宽度应各自定义。
  7. 硬件只认描述符，换模型就是换软件。契约里没有模型概念，Qwen3-0.6B 的移植只改了降级器、参考模型和导出脚本，RTL 和比特流一点没动。先对照硬件限制（K、地址空间、上下文）选模型，再用"小维度对 transformers、小维度上 RTL、全模型上板"三步验证。
  8. 板上的"不可能"值要按平台核实。"物理页号 0 不可能出现"在 x86 上大致成立，在 ZynqMP 上不成立；这个隐患从 v1.0 就存在，直到某次重启后才触发。
  9. 测试要能把队列塞满。v3.2b 去掉折叠的保护条件，原有测试全部通过，因为输出队列从来没满过。反压要强到让每个缓冲都到达上限。
  10. 省下存储不等于省下时间。v3.4 把状态减半，读请求数却没变，反而慢了 3%。先用计数器确认瓶颈是字节数还是请求数，再决定改数据格式还是改读取方式。
  11. 超出硬件限制的形状，先看能不能在软件里拆开。Gemma 的 K = 6912 超过 GEMV 上限，拆成两个 K 块、共用 scale、FP32 相加，就不用改 RTL。
  12. 大模型的数据会挤占 hugepage。1.6 GB 的文件读进页缓存后，内存碎片让 528 个 hugepage 凑不齐。申请失败时先释放干净的页缓存并整理内存，不必重启。
